## 胜负与指标的具体问题

旧 `Sample()` 在玩家死亡、Director 关闭时敌人全灭、或达到时限时结束。`win` 要求非 performance、玩家仍活着且敌人全灭；不要求队友存活，也不是 Uplink 撤离胜利。采样每 0.1 游戏秒进行，`survivalSeconds` 还会被夹到时间上限。因此它是轮次时长，不是角色存活时间；同一采样区间内的死亡与清敌先后无法从旧终点恢复。

本轮必须写明确 `terminationReason`，在事件发生时记录死亡时间，固定同帧终止规则，避免从不足时限反推死亡。建议玩家死亡优先于同一判定时刻的敌人清空；剩余敌人为零且玩家活着才算胜利，其他达到预算的轮次记 timeout。timeout 仍是已完成的实验结果，不是工具故障。

旧 `RecordDamage()` 的 `damageDealt` 合并玩家和队友伤害；`damageTaken` 仅主玩家；`timeToEngage` 是任何阵营第一次实际伤害。`DecisionCounts`、`DistanceTravelled`、EQS 与 stuck 汇总全部角色。`CoverUsage` 是查询选点被接受，不是掩体驻留。现有字段无法回答“队友为什么没帮上忙”，也不能把总 decision 次数解释为队友动作抖动。

最低限度的新指标应并列报告：

- **团队结果**：win/玩家死亡/timeout 数量、敌人存活数、玩家及队友终点状态、轮次时长；保留完整失败局。
- **玩家保护与输出**：玩家承伤、队友承伤、各自造成的实际伤害、各自实际获得的治疗；治疗记录已应用量，避免把溢出治疗算成收益。
- **队友存活**：死亡时刻或未观察死亡的 `-1`；`companionAliveSeconds` 仅为到角色死亡或本局结束的已观察存活时间。玩家先死而队友活着是竞争终止，不能把它当独立删失后直接画 Kaplan–Meier 生存优势。
- **动作稳定性**：Selected 动作驻留与切换、1 秒内 A→B→A 短反转、实际成功 BT 叶子的动作驻留、移动卡住秒、治疗贡献与射击次数。Selected 与 BT 成功/失败必须分开，不能将失败的叶子调用当动作完成；低切换也可能代表一直无效等待。
- **逐事件归因**：`episode_start/end`、带 source/victim 的 damage/heal、带角色的 death、decision 时的可用观测、分数、所选动作和实际执行。每条使用本局 game time；终点与事件可交叉核对。

本轮 runner 的一般治疗事件采用区间生命变化加实际伤害的账目核对，来源明确记为 `health_accounting`；这可说明实际恢复量，不能归因给某个施法者。队友 Support 的实际治疗贡献另由 `companionSupportHeals` 记录。该来源只允许出现在 heal，不能混入实际伤害来源。

`companionActionSeconds` 使用约 0.1 秒左端采样，统计近期成功叶子的状态；失败或成功记录过期后记 `waiting`。它不是逐帧精确执行驻留，更不是导航到达或攻击命中的证明。死亡时刻截断暴露窗口；episode 仍在下一次检查时终止，因此角色死亡时间与整局时长也不应强行视为相同。

胜率、承伤、输出、存活与稳定性同时展示，不以综合分数覆盖主终点。按整局时长直接除承伤或死亡也不能消除不同终止原因的混杂。

## 本轮已约定的小预算协议

这是待运行的协议，不是观察后筛选出的结果。地图与资产保持一致；Director 关闭，伤害真实生效，60 游戏秒，自动脚本玩家固定。baseline 与 improved 使用同一构建的开关，只改一个被失败轨迹支持的决策机制；priority 作为额外规则基线。不得同时改敌人、导航、治疗强度和 Utility 权重后把差异归给一个机制。

| 阶段 | 固定范围 | 用途 |
|---|---|---|
| 开发校准 | layout 0；敌人数 1、2、3；seed 2001–2003；baseline/priority，各组合三局，共 **18 局**。 | 不看 improved 选择难度；检查接敌、胜负逻辑和地板/天花板。 |
| 难度选择 | 取敌人数最大的 E，使 baseline 或 priority 至少一个策略在该 E 的三局中胜数为 1 或 2。 | 校准是开发集选择，不称无偏效果估计。若没有满足项，先查真实轨迹/终止判定，只调整一个场景变量并完整重跑声明后的开发集。 |
| 失败归因 | 使用开发轨迹选具体失败，记录观测→评分→选择→实际执行→结果；对照修复前后相同开发 case。 | 修复只针对明确机制；原始失败不能删。保留任何无改善或变差的开发结果。 |
| 冻结 | 写出固定 E、源码与资产、项目 DLL/EXE、脚本与协议文件摘要、所有政策、布局/seed 清单、终止规则及排除/重试规则。 | 冻结后不得根据 holdout 改策略、挑场景或换主指标。 |
| Holdout | layout 0 seed **9001–9006**；layout 1 seed **9101–9106**；baseline/improved/priority，同一固定 E，共 **36 局**。 | layout 1 为预定出生通道旋转 180°，仍是一张地图；不能宣称跨地图泛化。每个 seed/布局/条件跨三策略准确配对。 |

冻结时记录以上 36 个具体单元的执行顺序，按 seed 轮换策略先后，降低热机或运行顺序混淆；不以跑完一个策略再临时挑另一个策略代替配对。项目随机 seed 不保证 UE 导航、感知与调度位级相同。

主比较固定为 improved − baseline，priority 单独展示，两个 layout 分层列出。每个 holdout case 提供三行原始结果和配对差值；报告胜/败/超时与胜率区间，额外列配对胜负不一致的数量。连续指标给配对均值/中位数、范围及每局点，不把每帧或每次决策当独立样本。只有十二对、每布局六对，不足以做广泛优越性声明；平局、地板或负结果也发布。胜率不升但某次行为更合理时，只作机制改进证据。

已完成结果不能为改善统计而重跑替换。崩溃、日志/事件不完整、错误加载或哈希变化均记为基础设施失败并保留；修正后用新的完整批次/协议版本重做受影响比较，不能静默补一行。任何查看 holdout 后的策略修改必须提升版本并另设未使用数据。

## 可复核的交付要求

新 wrapper 的通过条件应包含精确配置与数量、唯一直接原生日志 marker、无引擎 warning/error/fatal/ensure、有限值与合理界限、显式胜负原因、事件与终点一致、源码/资产及实际项目二进制前后摘要一致。Editor 的通用 `UnrealEditor-Cmd.exe` 摘要不能替代 `UnrealEditor-AegisArena.dll`。启动/验证失败也应保存 provenance。渲染截图需检查真实 PNG 文件，截图请求不是证据；NullRHI 固定步长的耗时不是实际 FPS。

最终叙述保留三栏：**旧 v1.0 0/30 压力结果**、**开发失败及单机制修复轨迹**、**冻结后的全量 holdout**。三者各自使用版本、协议与样本范围；不相加、不重新命名旧证据。当前文档不会提前写任何新胜率或修复效果。
