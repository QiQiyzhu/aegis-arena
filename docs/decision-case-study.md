# 同伴活着，队伍却更好吗？

**决策：保留 Utility 作为可解释的策略选项，但不把它升级为“更优默认策略”。先修验收和指标，再决定优化目标。** 原生 30 对实验中，Utility 的同伴结束时死亡数为 6，Priority 为 25；与此同时，Utility 的累计输出更低、玩家累计承伤更高、轮次更短。这个结论来自已有 60 次原生运行的重新分析，本轮没有编译或执行 Unreal，也没有训练、调参或补跑新数据。

## 问题、约束与选择

游戏同伴有两个容易混淆的目标：让自己不死，以及帮助玩家完成战斗。工程问题不是“Utility 比 if/else 高级吗”，而是能否在有限预算下说明每个决策带来的代价，并避免错误验收污染判断。

已有系统使用授权观察快照、纯 C++ Utility 分数、迟滞切换、BT 执行与异步 EQS。Priority 保留作基线。现有证据仅覆盖一张地图、脚本玩家、四名敌人、两种策略各 30 个相同项目 seed；Director 关闭，最多 60 游戏秒，NullRHI 固定游戏步长。导航、感知与调度不保证位级确定，因此“配对”指配置与项目随机 seed 对齐，不是两个完全相同轨迹的反事实。

本轮审查排除了以下方案：

| 方案 | 排除或暂缓的原因 | 当前采用的做法 |
|---|---|---|
| 用 25→6 宣布同伴保护能力提升 | 只记录轮次结束状态，观察窗口也改变了 | 同时展示终点、时长、输出、承伤与反例 |
| 两边胜率都是 0，就只展示最好看的指标 | 胜率地板提示场景区分能力不足，不能删除主目标 | 保留 0/30，明确需要下一套预定实验 |
| 调低 EQS 距离过滤直到成功率好看 | 高失败率可能来自错误查询原点 | 读取 owner/pawn 坐标与实际 FailedTestIndex，修上下文 |
| 相信 Automation JSON 的 Success | 真实发生过测试 Actor 根本没执行 | 验证世界类型、具名断言与引擎错误信息 |
| 调滑块模拟“新策略胜率” | 只有两种策略的既有终点，没有新策略行为数据 | 滑块只重加权原始结果，标签明确为偏好指数 |
| 把同伴死亡数除以轮次时长当死亡风险 | 没有同伴死亡时刻，也没有正确的风险暴露时间 | 不输出生存曲线、死亡率或因果改善百分比 |

## 指标审查比挑选赢家更重要

原生 [ScenarioRunner](../Source/AegisArena/Private/AegisLab.cpp) 的 `Sample()` 每次取 `OwnedBots[1]` 是否存活写入 `companionDeaths`；玩家死亡、敌人清空或达到时限即结束整轮。`survivalSeconds` 实际记录整轮持续时间，并非同伴存活时间。`RecordDamage()` 将玩家阵营的实际伤害计为己方输出，只将主玩家受到的伤害计入玩家承伤。

因此存在两个具体解释边界：

1. **终止事件改变观察窗口。** Utility 平均 21.76 秒结束，Priority 为 25.38 秒。如果主玩家更早倒下，仍活着的同伴就不会继续暴露于风险。较低的同伴死亡终点可能同时包含行为收益和较短观察窗口。现有汇总行无法分离这两部分；不能把它叫作同伴生存时间提升。
2. **累计承伤不是纯粹的保护质量。** 治疗后可以再次受伤，故承伤超过初始生命有效。承伤高也可能因为活得更久、治疗更多；输出同样受轮次长度影响。简单按整轮秒数相除不能恢复缺失的逐事件信息。

| 既有观测终点 | Priority 均值/次数 | Utility 均值/次数 | Utility − Priority |
|---|---:|---:|---:|
| 胜利 / 30 | 0 | 0 | 0 |
| 结束时同伴死亡 / 30 | 25 | 6 | −19 |
| 累计己方伤害 | 170.46 | 139.40 | −31.06 |
| 累计玩家承伤 | 106.68 | 126.06 | +19.38 |
| 轮次时长，游戏秒 | 25.38 | 21.76 | −3.61 |

按 seed 看：结束时同伴存活这一终点，Utility 有 20 对更高、1 对更低、9 对相同；输出则有 22 对更低、2 对更高、6 对相同。不是只有均值掩盖了一个偶然异常。

在“同伴终点存活、输出更高、累计玩家承伤更低、轮次更长”这四个已公开偏好上，23 对存在取舍，3 对 Priority 端点支配，1 对 Utility 端点支配，3 对相同。这里的“支配”只是这些选定终点上无劣项且有优项；不包含所有游戏体验，也不代表因果优势。唯一 Utility 支配的 seed 1025 仅多约 0.1 秒，其余三项相同，不应包装成有实用意义的全面胜出。比较容差为原单位 0.0001，原始数值保留。

## 可解释机制与尚不能确认的原因

[纯规则](../core/include/aegis/rules.hpp) 中，自身低血量提高 Retreat 分数；Support 受盟友已知、技能就绪与盟友血量门槛约束；迟滞减少轻微分差造成的动作切换。该机制可以解释为什么会出现更偏向自保的行为，但**终点数据没有给出动作驻留时间、治疗时间线或归因消融，不能确认少死亡的全部原因**。

另一项是可以直接定位的集成缺陷。EQS Request 由 Controller 持有，但默认 Controller 不随 Pawn 移动。实际诊断中查询 owner 仍在 `(-1200,0,100)`，Pawn 已移动至 `(-9.06,419.09,90.15)`；攻击候选全部被 Distance 测试过滤。修复 `bAttachToPawn=true` 后保持原有查询与威胁上下文协议，未放宽过滤。战术 BT 任务也从无条件 Success 改为只有 pending、有效移动或已到达有效点时继续成功，否则允许既有 fallback。最终原生失败查询为 16/878 与 8/892。[坐标、候选记录与修复](eqs-debugging.md)。这证明了集成正确性改进，不能代替策略效果证据。

## 一次被拆穿的假成功

第一层证据是 [旧 Automation JSON](../evidence/unreal/before-eqs-fix/functional-false-positive/index.json)：它显示成功。第二层是 [同次引擎日志](../evidence/unreal/before-eqs-fix/functional-false-positive/engine.log)：错误地图没有 Functional Test Actor，出现 `No functional testing script`。继续显式加载测试地图后，测试实际运行在 Editor World，真实战斗断言暴露失败。这两个问题都曾让“进程正常退出/结果文件存在”看起来合理。

修复不是隐藏日志，而是要求 fixture 在已 BeginPlay 的 PIE World 执行。当前 [验证器](../scripts/run_unreal_functional.py) 同时要求：

- 恰好一个完成且无告警的结果，没有失败、未运行或运行中项。
- `WorldType=3 | BegunPlay=1` 的明确成功 marker。
- 12 条具名真实世界断言全部出现，包括 trace、冷却、友伤、死亡治疗、移动 Querier 和 missing-query fallback。
- 没有 handled ensure、missing-script 或其他已知失败 marker。

[最终引擎日志](../evidence/unreal/functional/engine.log) 证明这些条件实际满足。Python 回归则验证 JSON-only success、漏断言和 ensure 会被拒绝。二者职责不同：Python 测试不能证明 Unreal 跑过，真实引擎日志也不能替代对验收器拒绝路径的测试。

## 偏好排序如何计算

导出的四个量依次为 `结束时同伴活着(0/1)`、`累计己方伤害`、`累计玩家承伤`、`轮次秒数`。固定参考量纲为 `1 / 100 / 100 / 60`；方向为 `+ / + / − / +`。

```text
score = Σ(weight[i] × direction[i] × observedEndpoint[i] / scale[i]) / Σ(weight)
```

权重必须有限、非负且总和大于零；得分可为负，不是概率。参考量纲是公开的解释选择，不使用随样本改变的 min-max，也不掩盖尺度/权重的主观性。改变网页滑块不会改变 Utility 实际权重或角色行为。

| 演示偏好（按上述顺序） | Priority 分数 | Utility 分数 | 既有终点排序 |
|---|---:|---:|---|
| 结束时同伴活着：65/15/15/5 | 0.2252 | 0.5582 | Utility 在前 |
| 输出与坚持：10/45/25/20 | 0.6016 | 0.4647 | Priority 在前 |
| 较低累计玩家承伤：10/15/65/10 | −0.3788 | −0.4940 | Priority 在前 |

这些是本轮事后审查的偏好示例，不是预注册实验目标。排名变化说明结论依赖目标定义；它不能消除终止窗口混杂，也不能预测新的混合策略。未给复合得分置信区间，不使用“统计显著更优”的措辞。

## 下一项实验应先补什么

1. **先固定产品问题。** 要帮助玩家赢，还是让同伴不成为负担？两者写成主、次指标；保留失败率与输出/承伤护栏，不能运行后挑胜出项。
2. **先补事件再讨论生存。** 记录双方死亡时间、治疗事件、终止原因和动作驻留。玩家死亡导致同伴观察停止，应作为依赖性的竞争终止事件处理，不能直接套用独立删失假设。是否让玩家死亡后继续模拟必须事先说明，因为那会改变实验问题。
3. **确认场景有区分能力。** 预先固定一套较容易的场景，同时保留当前压力场景；运行前冻结未使用 seed 与重复次数。这里只提出下一实验，没有新结果。
4. **再做针对机制的消融。** 单独改变自保项或迟滞，记录行为占比与团队终点；不要同时改敌人、导航、治疗与奖励函数。新版本与旧版本独立保存。

这次工作的价值是让策略选择可以被质疑、复现和修正，而不是在负面结果上添加一个更漂亮的赢家标签。
