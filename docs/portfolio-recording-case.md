# 录制工具案例：角色停住，并不一定是游戏 AI 决策失败

这次修复发生在 `AAegisPortfolioCapture`，即用正常玩家输入完成演示的录制驾驶器。游戏中的队友 / 敌方战术策略、感知权限、伤害和资源规则没有因此调整。它是工具可靠性案例，不能替代 [v1.4 的真实 AI 失败案例](decision-lab-case.md)，也不属于策略 holdout、真人试玩或胜率提升证据。

## 原始失败与定位

`preview-04` 完成原生运行、正确的 1920×1080 图像和账本验收，但游戏结果为 Lost：到 180 个游戏秒超时。这里的验收 PASS 表示证据完整，并不表示通关。

在录制时间 `videoSeconds=34.033`，玩家停在 `(550.739, -816.217)`，生命 124。此时是第 2 波的第 1 个 relay，进度 2.4 / 4；该点距旧目标 `(850,-850)` 约 301.16 cm，比驾驶器的 120 cm 停止距离远，也在 260 cm 占点范围外。后续队友补完第 1 个 relay，约 37.13 秒切到第 2 个 relay，但玩家仍留在原地，距新目标约 1897.88 cm。敌人已全部清除，最终只完成 1 个阶段、击杀 7 名敌人。

这不是“到目标后等待”的正常状态。停滞早于 relay 切换，也早于约 38 秒开启的 F1 诊断面板，不能把面板遮挡直接当成原因。

原驾驶器每 0.4 秒清空旧路径，再调用同步寻路；只有路径有效且完整时才保存路径点。路径为空或已耗尽，方向就是零，然后驾驶器主动松开 WASD。因此单看游戏画面无法判断是寻路失败、输入丢失，还是碰撞挡路。

`driver-diagnostic-05` 增加了路径点数、路径索引、目标 / 方向、驾驶器记住的按键、PlayerController 实际按键、Z 坐标、速度与输入许可记录。同时试过一个范围很小的“记住按下但实际没按下时重发按键”处理。

05 重现了同一停滞，关键记录为：

| 录制时间 | 路径点 / 索引 | 方向 | 记住 / 实际 WASD | 角色状态 |
|---|---|---|---|---|
| 34.033 s | 0 / 0 | `(0,0)` | 两者均全松开 | `combatEnabled=true`，`moveInputIgnored=false` |
| 35.033 s 以后 | 0 / 0 | `(0,0)` | 两者均全松开 | 速度 0，Z 约 90.15，位置不变 |

按键重同步计数为 **0**。这个尝试没有触发，也没有改变 Lost 结果。证据支持的直接机制是“录制器没有可接受路径，于是没有输出移动输入”；本次复现不支持“按键状态丢失”。

## 最终只修改录制器的寻路输入

当前 [AegisPortfolioCapture.cpp](../Source/AegisArena/Private/AegisPortfolioCapture.cpp) 的 `Drive()` 使用以下处理：

1. 用 `Player->GetNavAgentLocation()` 取得导航脚底位置，取代 capsule 中心位置。
2. 起点和目标都用 `(180,180,250)` cm 的有限范围投影到导航面。
3. 在投影点间请求完整导航路径。路径索引从 0 开始，只有实际靠近 90 cm 内的路径点才跳过，避免无条件跳过投影后的起点。
4. 仍通过 `SetKey()` / `PlayerController::InputKey` 输出普通 WASD，保留正常角色移动、碰撞和技能冷却。

UE 5.8 的 `ACharacter::GetNavAgentLocation()` 返回角色移动组件的脚底位置；此前传给同步寻路 helper 的是 Actor capsule 中心。该 helper 直接构造寻路查询，并未先做这里的显式起终点投影。

按键重同步尝试已全部撤回；最终 `SetKey()` 恢复普通的按下 / 松开处理，遥测保留。没有使用瞬移、直接改位置、伤害注入、清除敌人或修改胜利条件。

最终改动同时涉及脚底坐标、起终点投影和初始路径索引。现有记录没有保存 04 原始查询的内部 Recast 错误码，因此不能进一步断言只有其中某一行是唯一底层原因，也不能声称修复了所有可能的导航失败。

## 06 的真实位移证据

`driver-diagnostic-06` 继续使用相同地图资产、seed 1101、1920×1080 请求、30 FPS 固定步长和相同角色 / 资源预设。它关闭 PNG 保存以缩短诊断周转，`frames=0`，不能作为最终录像或最终画面质量证据。

这次不仅看到“路径被接受”，还看到以下连续实际运动：

| 录制时间 | 实际位置 cm | 路径与输入 |
|---|---|---|
| 26.333 s | `(553.346,-810.553)` | 距旧停点仅 6.24 cm；2 个路径点，实际 W+D 按下 |
| 26.733 s | `(689.505,-778.348)` | 路径包含 3 个点、当前索引 2；实际 W 按下 |

这 0.4 秒的净位移为 **139.92 cm**，距旧 relay 目标由 299.27 cm 降到 175.76 cm；沿途记住的按键与实际按键相符。这是经过旧停点附近并继续运动的证据，没有把接受命令当成到达。

随后 32.533–35.533 秒，玩家向 `(0,1000)` 的第 2 个 relay 移动：从 `(886.282,-45.296)` 到 `(121.111,872.308)`，净位移 **1194.77 cm**，目标距离从 1370.45 cm 降到 175.99 cm。这段 31 个样本均有至少 2 个路径点、至少一个实际移动键，且 `heldWasd == actualWasd`。进入圈后正常停住，进度从 0.2 增至 4；约 39.33 秒进入阶段间隔。

06 的轨迹在更早阶段已经变化，经过旧停点的时间也提前了。因此这些记录证明修复后的录制器能够经过原失败区域并完成后续导航，不是完全相同世界状态下的逐帧反事实比较。

## 结算与验收边界

06 真实 Won，任务时长 **83.4 游戏秒**；会话含简报为 87.4 游戏秒，录制时间轴为 98.5 秒。111 条系统事件已经由严格 validator 重新逐笔核对：

- 12 次真实击杀、3 次阶段完成；名义收入 `12×12+3×25=219`，实际入账 185、溢出 34。
- 3 次 Q、1 次 E，支出 `3×35+40=145`；最终余额 `60+185-145=100`。
- E 实际恢复自身 14 HP、同伴 0 HP；不是额定上限 30 HP。
- 实际友方输出 1260，玩家承伤 56，同伴承伤 42；没有 fixture damage。

保存的 provenance 为 PASS，源码、资产、启动器 / 项目模块的运行前后哈希一致。额外只读调用 `validate_system_capture()` 再次通过账本、治疗、伤害角色归属和终局对应检查。原生记录明确 `scriptedPlayer=true`、`fixtureDamage=false`、`humanPlaytest=false`。

这些是相同预设下的定向工具复现，只有一次修复后诊断成功。没有证明玩法更平衡、真人更容易通关或队友 AI 策略更优。独立包和最终完整录像另行验收，失败局继续保留。
