# Aegis Arena: playable showcase priorities

Research and source audit: **2026-09-10**. Baseline source revision: `daabbe2`. This document records the starting defects and proposed acceptance criteria for the current upgrade; it is not a claim that every item below is implemented or passed. Use [status.md](status.md) for delivered evidence.

The strongest practical direction is a short, understandable arena encounter that exposes the companion's decisions through play. The repository already contains unusually inspectable AI evaluation evidence. The next improvement is to let someone launch the packaged game, understand their role, aim, receive combat feedback, reach an outcome, and try again without reading development documentation.

## Four highest-value improvements

The defects below were found by reading `AegisLab.cpp`, `AegisCharacter.cpp`, their headers, `DefaultInput.ini`, and the acceptance ledger at the baseline revision. They are source-level findings; they do not add new runtime evidence.

| Priority | Baseline defect and player impact | Feasible implementation direction | Acceptance target |
|---|---|---|---|
| 1. Shipping player HUD and onboarding | `AAegisDebugHUD::DrawHUD` puts all content inside `!UE_BUILD_SHIPPING`. The playable Shipping game therefore loses health, objective, controls, and any other HUD information with the diagnostics. Navigation failure is logged but has no player-facing status. | Draw a compact player HUD in every build: objective, player/companion health, threats or progress, weapon readiness, controls, and loading/failure state. Keep developer AI internals behind their existing boundary. | At 1280×720 and 1920×1080, a real Shipping window shows legible controls, status, and health without clipping or developer internals. Death and loading do not leave misleading live-game instructions. |
| 2. Complete encounter and retry loop | `StartInteractive` spawns four enemies, including one elite, enables ongoing director spawns, and installs only `ApplyDirector` as its timer. The interactive path has no explicit victory/defeat, restart, or pause flow. Dead players remain in the world. Its 50-owned-bot cap is a lifecycle bound rather than an explained objective. | Add explicit encounter states, finite progression, a clear success condition, defeat, pause, and restart. Start gently enough to teach movement and firing; later progression can expose harder enemies. Keep research scenarios and paired evaluation seeds separate. | Exercise win, loss, pause/resume, and repeated restarts in a game world. Restart resets player health, movement, collision, cooldown, bot/controller population, timers, and encounter UI. Input cannot keep dealing damage during pause or after an outcome. |
| 3. Aim and combat feedback | Player fire is bound only to `IE_Pressed`; firing uses actor forward direction, while `MouseX` changes yaw. A square primitive does little to explain facing. The only ranged shot line is `DrawDebugLine` inside `!UE_BUILD_SHIPPING`, so it disappears from the delivered build. | Use cursor-directed aiming with visible facing/reticle and hold-to-fire gated by the existing combat cooldown. Provide Shipping-safe shot/impact presentation and a concise readiness indicator. Preserve faction filtering and physical occlusion. | Aiming in each quadrant points shots correctly; walls block shots; allies take no damage; holding/releasing fire obeys cooldown and stops as expected; death/restart clears held input. Shot and hit feedback are visible in Shipping, including a missed shot. |
| 4. Companion identity and tactical readability | Companion differs mainly by green tint; enemy/elite distinction is also primarily color and scale. Damage has no explicit player-facing reaction in these source files, and death only disables movement/collision and changes tint. Development diagnostics expose raw actor names and utility values rather than explaining the allied role. | Use role labels and shape/facing cues alongside color, restrained damage/death feedback, and a short companion state label derived from its real current action. Make cover and threat direction easy to read. Add original sound cues as a subsequent presentation pass if they can be packaged and verified. | A viewer can identify player, companion, ordinary enemy, elite, and dead actors without relying on color alone. Any companion action label matches the live policy state; it must not claim protection or superior survival from the historical endpoint comparison. Feedback remains readable during several simultaneous attacks. |

These priorities are this audit's design judgment, informed by the cited criteria. They are not competition requirements. The sound pass is an explicit remaining quality opportunity if not delivered; visual traces are not evidence of audio design.

## Relevant official Unreal references

- [Creating user interfaces](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-user-interfaces-with-umg-and-slate-in-unreal-engine), UE 5.8 documentation: official entry point for UMG, Slate, text/localization, accessibility, and UI testing. An incremental Canvas HUD can address this small project's immediate gap; a UI framework migration is not itself a player benefit.
- [DPI scaling](https://dev.epicgames.com/documentation/en-us/unreal-engine/dpi-scaling-in-unreal-engine), UE 5.8 documentation: UMG supports automatic resolution scaling with configurable rules and curves. If this pass retains direct Canvas drawing, implement and inspect its own viewport-aware layout; do not assume UMG's scaling automatically applies to Canvas coordinates.
- [Enhanced Input](https://dev.epicgames.com/documentation/en-us/unreal-engine/enhanced-input-in-unreal-engine), UE 5.8 documentation: supports action states, mapping contexts, remapping, and contextual priorities. It is a suitable later path for gamepad/rebinding. Hold fire and pause must have deliberate press/release/state behavior even if the existing input system is retained for this pass.
- [Screen reader support](https://dev.epicgames.com/documentation/en-us/unreal-engine/supporting-screen-readers-in-unreal-engine), UE 5.8 documentation: Epic documents an experimental accessibility feature and supported UMG widgets. Visible text and role labels alone do not establish screen-reader support; that would require a separate implementation and validation.

The opened API pages for cursor deprojection and HUD did not return useful API documentation in this research. Implementation signatures should be checked in the installed UE 5.8 headers rather than inferred from those empty web responses.

## Evidence needed for the next showcase

1. Compile changed Unreal targets and run relevant game-world tests. Preserve the existing combat/AI acceptance gates. If interactive tuning changes shared combat behavior, do not reuse historical evaluation results as evidence for the new behavior.
2. Launch the resulting standalone Shipping package. Inspect real input, objective progression, defeat/retry, pause, readable UI, and feedback. A successful compile, a NullRHI test, and a rendered launch prove different things.
3. Capture a fresh, continuous 30–60 second playable sequence showing actual aim, firing, companion behavior, and an outcome or progression. Record build identity and capture conditions. The existing 2 fps GIF remains useful evidence of the earlier native scene, not smooth-play footage of this update.
4. List untested or unfinished items explicitly: audio, controller/rebinding, accessibility, and broader difficulty playtesting as applicable. Preserve the observed 0/30 versus 0/30 native policy results and the termination-window confound. Easier interactive progression does not retroactively demonstrate policy superiority.

No competition submission, commercial-readiness claim, new frame-rate claim, or new policy-quality result follows from this research document.
